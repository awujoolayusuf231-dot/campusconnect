# Deployment guide

CampusConnect is a static single-page app (Vite build) plus a dedicated Supabase project. It never connects to the whiteshirt.fun project.

## 1. Supabase project (one per environment)
Use a separate Supabase project per environment (e.g. `CampusConnect01` = current; create a second for staging/production if you want isolation).
1. Apply every file in `supabase/migrations/` **in filename order** (SQL editor, or `supabase link` + `supabase db push`). Never edit an applied migration; add a new one. Migration `20261031000013_google_oauth_profile_usernames.sql` reads standard Google name metadata to create readable profile usernames and updates existing Google profiles that still have generated `user_*` handles.
   The Past Questions student catalog-add flow requires `20261112161500_allow_student_catalog_entries.sql` after `20261112000019_past_questions_library.sql`; `20261113000020_fix_past_question_upload_rls_recursion.sql` fixes upload-policy recursion. Study Notes requires `20261113000021_study_notes_repository.sql` after those migrations; it adds `study_notes.review` for admins/moderators, while the owner has the permission automatically. Grant it to other staff through Admin > Staff. Assignment Discussion Rooms requires `20261113000022_assignment_discussion_rooms.sql` after Study Notes; it adds the persisted course discussions, replies, private attachment policies, reports, and notifications. Apply `20261113000023_fix_assignment_discussion_author_profile_fks.sql` after it to align author relationships with PostgREST profile embeds, then `20261113000024_fix_assignment_discussion_rls_helper_permissions.sql` to let RLS safely use private block/profile helpers. Project Collaboration, Inter-University Competitions, and Voice Spaces require `20261115000033_projects_competitions_voice_spaces.sql` after the profile/RBAC, social/block, communities, notification, and storage foundations. It creates private asset buckets and defaults the three feature flags to enabled; admins can disable them under Platform > Settings and flags. Migration `20261126000052_voice_presence_notification_preferences.sql` adds the persisted live start time, privacy-redacted active Voice Space presence, ended-room read access for previously eligible users, and master/category notification preferences. CampusConnect01 has migrations applied manually with a mismatched CLI history; do not run `supabase db push` there until that history is reconciled. Apply only a reviewed, missing migration in the SQL Editor.
   Public post impressions/views, saved posts, comment likes/replies, and comment reshares require `20261116000036_social_post_interactions_metrics.sql` after the social visibility helpers. Private account-wide post/comment analytics and comment impressions/views require `20261116000037_private_social_analytics_comment_impressions.sql` after migration 36. It depends on `supabase/manual-sql/01_post_visibility.sql` and the impression foundation in `sql-file/20261101110000_post_impressions_profile_views.sql`; those foundations require hashtag Migration A (`sql-file/20261101100000_hashtags.sql`). Apply only missing SQL files, in their documented prerequisite order; do not rerun an applied SQL file or migration. The `my_social_analytics` and `my_comment_analytics` RPCs return only the signed-in user's own totals or analytics for comments they authored/on their posts; viewer identities and impression records are never available to clients. Include `select public.purge_comment_analytics(5000, null, 400);` in the same scheduled maintenance job as `purge_analytics_dedupe`, repeating while the returned `more` field is true.
2. Auth > URL Configuration: set **Site URL** to your production origin (e.g. `https://campusconnect.example.ng`) and add it plus `http://localhost:5173` to **Redirect URLs** (use `https://your-domain/**`).
3. Auth > Providers > Email: keep **Confirm email ON**. Keep "Secure password change" on.
4. **Auth > Password security (dashboard only, cannot be set from code):** turn ON **Leaked password protection** (the Supabase security advisor flags it as a WARN while off), and raise the **minimum password length** to at least 8 (the app enforces 8-72 in the form, but the server setting is the real rule).
   Auth > Rate limits and (optionally) CAPTCHA: enable bot protection for sign-up and password reset before launch.
5. **Auth > SMTP:** the built-in mailer is only for local testing and is heavily rate-limited. For a live project, verify the sender domain in Resend and configure SMTP with host `smtp.resend.com`, port `465` (implicit TLS), username `resend`, the Resend API key as password, a verified sender address, and sender name `CampusConnect`. Keep the SMTP password in the Supabase dashboard. Copy the branded templates from `supabase/templates/` into the corresponding hosted Auth template fields and enable password/email-change security notifications. Supabase Auth continues to create and validate these links; do not replace its auth URLs with a direct Resend send.
6. Storage: migration 0005 creates `avatars` (public, 2 MB) and `post-images` (private, 5 MB); migration 00015 adds `profile-covers` (private, 2 MB), migration 00016 adds `community-covers` (private, 2 MB), migration `20261112000019_past_questions_library.sql` adds the private `past-questions` bucket, migration `20261113000021_study_notes_repository.sql` adds `study-notes` (private PDFs, maximum 20 MB), and migration `20261113000022_assignment_discussion_rooms.sql` adds `assignment-discussions` (private PDFs, maximum 10 MB). Confirm their visibility, file-size, and MIME limits in Storage. Avatar images remain public. Post images are read through the authenticated `post-image` Edge Function so current post visibility rules still apply; deploy it with `supabase functions deploy post-image` whenever deploying the image-reading frontend. Its gateway JWT verification is disabled to allow CORS preflight, while the function validates the bearer token itself. Profile-cover reads follow profile visibility; community-cover reads are limited to the currently selected cover of a visible community, while upload/update/delete require the active community owner. Existing profile covers are still public in `avatars` until each owner uses **Make cover private** in Profile > Edit, or removes/replaces the cover. Do not mark either cover bucket public. Apply migrations 00015, 00016, and 00018 before deploying their respective profile/community cover UI.
7. Database > Replication: `messages` and `notifications` must be in the `supabase_realtime` publication (migration 0009 adds them).
8. Backups: check your Supabase plan for daily backups / point-in-time recovery and turn them on before real students sign up. Test a restore into a scratch project once.

## LiveKit Voice Spaces

Live audio requires a LiveKit project in addition to the Supabase migrations. Apply `20261115000033_projects_competitions_voice_spaces.sql`, `20261115000035_voice_room_host_controls.sql`, and `20261126000052_voice_presence_notification_preferences.sql` in filename order after their prerequisites. Set `LIVEKIT_URL` (the LiveKit WebSocket URL), `LIVEKIT_API_KEY`, and `LIVEKIT_API_SECRET` as Supabase Edge Function secrets using the dashboard or `supabase secrets set`. Do not put these credentials in Git, a browser `.env` file, or any `VITE_` variable. Deploy both functions with gateway JWT verification disabled: `supabase functions deploy livekit-token --no-verify-jwt` and `supabase functions deploy livekit-room-control --no-verify-jwt`. This setting lets CORS preflight requests reach the functions; each function independently validates the user's Supabase bearer token. Redeploy after changing either function or its settings. The control function uses the database's host authorization before changing participant publish permissions. Participants join with open microphones by default; the host can lock microphones, then approve raised hands. The connected call stays alive across in-app route changes and attempts to use browser media-session controls. Background audio while a browser or mobile OS suspends the app remains platform-dependent and should be tested on target devices.

## Admin account deletion

Apply `20261115000034_admin_account_deletion_actions.sql` after the account-deletion request and admin-audit foundations. Deploy `admin-delete-account` with `supabase functions deploy admin-delete-account`. The function verifies the moderator's session, records approval, and deletes the target Auth user through the service-role API; the service-role key is provided automatically by Supabase and must never be exposed to the browser. If Auth deletion fails, the request is restored to pending. Rejecting a request keeps the account. Permanent account deletion cascades associated database records; review your Storage retention/cleanup requirements separately because database cascades do not remove Storage objects.

## Correcting an unverified signup email

The verification modal corrects a mistyped address through the `correct-unverified-signup-email` Edge Function. Apply `20261126000048_unverified_signup_email_correction.sql` and deploy it with `supabase functions deploy correct-unverified-signup-email` before relying on this action. Its `verify_jwt = false` setting is intentional: the function checks the original email/password and confirms the account is still unverified itself.

The message “Could not reach the secure email correction service” means the browser could not complete the function request; it is not the password-rejection response. Confirm the function is deployed to the same Supabase project configured by `VITE_SUPABASE_URL`, then check Edge Function logs and the browser console/network for connectivity or CORS failures. If the function responds but the original credentials are wrong, the modal instead asks the user to check the original signup email and password.

## Resend Auth and transactional email

Supabase Auth delivers registration verification/resend, email changes, magic links, and password recovery through its configured SMTP provider. The project templates are in `supabase/templates/`. Local Supabase keeps its local email catcher; the Resend SMTP block in `supabase/config.toml` is intentionally commented so development does not send real messages.

For production/staging, verify a Resend sending domain and use the same verified sender address in Supabase Auth SMTP and the email worker. Store credentials only as Supabase server-side secrets:

```sh
supabase secrets set \
  RESEND_API_KEY="<Resend API key>" \
  RESEND_AUDIENCE_ID="<Resend audience ID>" \
  RESEND_FROM_EMAIL="CampusConnect <notifications@your-verified-domain>" \
  CAMPUSCONNECT_APP_URL="https://your-campusconnect-domain" \
  CAMPUSCONNECT_EMAIL_WORKER_SECRET="<new random worker secret>" \
  CAMPUSCONNECT_CONTACT_SYNC_SECRET="<different new random contact worker secret>" \
  RESEND_WEBHOOK_SECRET="<Resend webhook signing secret>"
```

`RESEND_API_KEY`, `RESEND_AUDIENCE_ID`, `RESEND_FROM_EMAIL`, and the worker secrets are read only by Edge Functions. Put the API key separately into Supabase Auth > SMTP as the password (user `resend`, host `smtp.resend.com`, port `465`). Never put any of these values in `.env.local`, frontend build variables, `VITE_*` variables, SQL source, or Git. The browser only requests password reset/verification from Supabase Auth; Resend credentials never reach it.

1. Apply `20261126000049_resend_email_delivery.sql` once, after the notification, user-preference, and account-standing migrations. For CampusConnect01, whose migration history is manually maintained, inspect the database first and apply only if the objects are not already present.
2. Deploy both functions: `supabase functions deploy process-email-outbox` and `supabase functions deploy resend-webhook`. Their `verify_jwt = false` settings are required: the worker authenticates its own shared secret, and the webhook verifies Resend's Svix signature against the raw request body.
3. Store the project URL and the exact `CAMPUSCONNECT_EMAIL_WORKER_SECRET` in Supabase Vault as `campusconnect_project_url` and `campusconnect_email_worker_secret`. Enable `pg_cron`, `pg_net`, and Vault, then run [`enable_email_outbox_cron.sql`](../supabase/manual-sql/enable_email_outbox_cron.sql). The database also makes a best-effort immediate dispatch; the minute cron is the retry/fallback path.
4. Apply `20261126000050_resend_audience_contact_sync.sql`, deploy `sync-resend-contacts`, and set the matching `CAMPUSCONNECT_CONTACT_SYNC_SECRET` Edge Function secret. In Vault, create secrets named `campusconnect_project_url` (the project's `https://<project-ref>.supabase.co` URL) and `campusconnect_contact_sync_secret` (the exact same value as the Edge Function secret). For example, in the Supabase SQL Editor, replace the placeholders and run the two `vault.create_secret(...)` statements at the top of [`enable_resend_contact_sync_cron.sql`](../supabase/manual-sql/enable_resend_contact_sync_cron.sql), then run the rest of that script. If either secret already exists, update it rather than creating a duplicate. Do not commit the real secret. Contact changes are queued on signup, email verification, and preference changes; immediate dispatch is best-effort, and the minute cron retries failures. Admins with `settings.manage` can start the backfill and view aggregate counts under Admin > Resend contact sync. The backfill queues only verified users with recorded marketing consent; users without an email, consent, or verified email are reported as skipped. New contacts are synced only after email verification and remain unsubscribed unless explicit marketing consent is present.
5. In Resend, create a Segment for CampusConnect and set `RESEND_AUDIENCE_ID` to that Segment's ID (the environment-variable name is retained for compatibility). The function uses Resend's current Contacts and Segments API, adding contacts to this Segment and keeping non-consenting or unverified contacts unsubscribed. Add a webhook for `https://<project-ref>.supabase.co/functions/v1/resend-webhook`. Subscribe to `contact.updated` as well as `email.sent`, `email.delivered`, `email.delivery_delayed`, `email.bounced`, `email.complained`, `email.failed`, and `email.suppressed`. Save its signing secret as `RESEND_WEBHOOK_SECRET`. The endpoint verifies Svix signatures and only records unsubscribe events from the configured Segment.
6. In Supabase Auth settings, keep email confirmation and secure password changes enabled. Use the HTML files in `supabase/templates/` for the confirmation, recovery, email-change, and magic-link templates. Enable the password-changed and email-changed notifications. Set the production site URL and redirect allowlist to include the app's `/auth/callback` and `/reset-password` routes. Keep CAPTCHA and Auth rate limits enabled; tune the email limit to the expected volume only after abuse controls are configured.
7. Email activity is opt-in under Account Settings → Notification settings (`notify_email` defaults to false) and respects each existing notification category preference, account standing, and block relationships. Platform announcements and moderator warnings remain eligible even if activity email is disabled. A welcome email is queued once, only after Auth confirms the email address. Message bodies and private post contents are never included in notification email. Marketing email consent is separate from all transactional and activity notification settings.
8. Test a new signup with marketing consent both off and on, confirm that an unverified or non-consenting address stays unsubscribed, verify an opted-in account before it can receive broadcasts, run the admin backfill, and confirm duplicate contact handling, retry after a transient Resend failure, permanent failure reporting, and unsubscribe persistence after subsequent profile/preference syncs. Check the Admin > Resend audience aggregate counters and the Edge Function logs. Keep verification and password-reset flows tested independently; those continue through Supabase Auth SMTP.
9. Test a new signup and resend, correction of an unverified email, recovery request and reset link, password-change notice, confirmation-to-welcome flow, opt-in activity email, activity opt-out, and an announcement/moderation notice. Check Supabase Auth logs for Auth SMTP errors and Resend's Emails view for Auth and worker messages. For worker mail, `email_outbox.status = 'accepted'` means Resend accepted the API request; a verified `email.delivered`, `email.bounced`, `email.complained`, or other terminal webhook updates that status. Temporary API/network failures retry with exponential backoff (up to 8 attempts); the stable Resend idempotency key prevents duplicate delivery on retries. Check `pending`, `failed`, and `last_error` rows if mail is not accepted. Auth SMTP events are visible in Supabase Auth logs and Resend; they do not have an `email_outbox` row because Supabase Auth owns those sends.

Local unit tests use mocked Resend responses to verify acceptance, transient retry, permanent failure, idempotency, template escaping, and webhook signature validation. They do not prove live deliverability. A real successful delivery test requires a verified Resend domain/API key, deployed functions, the SMTP dashboard configuration, and the webhook/cron setup above. Local Supabase uses its mail catcher and the email worker intentionally refuses to send through Resend from a local Supabase URL.

## Firebase Browser Push

LiveKit credentials do not configure Firebase push. Migration `20261113000028_push_notifications.sql` enqueues notifications, but an Edge Function worker must be scheduled to deliver them.

1. In Supabase Edge Function secrets, set `FIREBASE_SERVICE_ACCOUNT` to the Firebase service-account JSON and `PUSH_WORKER_SECRET` to a new random secret. Deploy the worker with `supabase functions deploy process-outbox`. The same worker secret must also be stored in Supabase Vault; never commit either secret.
2. Ensure `pg_cron`, `pg_net`, and Vault are enabled. Store the project URL and the exact `PUSH_WORKER_SECRET` in Vault as `campusconnect_project_url` and `campusconnect_push_worker_secret`. Then review and run [`enable_push_outbox_cron.sql`](../supabase/manual-sql/enable_push_outbox_cron.sql) in the Supabase SQL Editor. It schedules delivery every minute.
3. In Firebase Console, register a Web app under the same Firebase project used for the service account. Copy its `apiKey`, `appId`, `messagingSenderId`, and `projectId`. Under **Project settings → Cloud Messaging → Web Push certificates**, generate a key pair and use its public key as the VAPID key. Enable the Firebase Installations API and Firebase Cloud Messaging API (HTTP v1) in the associated Google Cloud project. If the web API key is restricted, allow Firebase Installations API and the deployed site's HTTP referrer. Ensure the service account can send FCM messages. Its `project_id` must match the browser app's `VITE_FIREBASE_PROJECT_ID`.
4. Configure the browser-safe values in the frontend hosting/build environment: `VITE_FIREBASE_API_KEY`, `VITE_FIREBASE_APP_ID`, `VITE_FIREBASE_MESSAGING_SENDER_ID`, `VITE_FIREBASE_PROJECT_ID`, and `VITE_FIREBASE_VAPID_KEY`. These are public web-app values, not the service-account JSON. Rebuild and redeploy after changing them; `.env.local` only affects local development. Then sign in, open Account Settings → Notification settings, choose **Enable on this device**, and allow browser notifications. This explicit click opens the browser permission prompt; push does not prompt automatically. Production push requires HTTPS. Installing the PWA is not required in desktop Chrome/Edge; iPhone/iPad requires iOS/iPadOS 16.4+ and adding the site to the Home Screen before enabling web push.
5. To diagnose delivery, check **Edge Functions → `process-outbox` → Logs** and run `select status, last_error, count(*) from public.push_outbox group by status, last_error order by status;`. No queued rows usually means no notification was generated; pending rows indicate the worker is not draining the queue; failed rows show the latest delivery reason. Confirm the cron job is active with `select jobname, schedule, active from cron.job where jobname = 'campusconnect-push-outbox';`.

For the immediate-dispatch and richer-copy update, apply `20261117000041_push_outbox_immediate_dispatch.sql`, then deploy `process-outbox` with `supabase functions deploy process-outbox`, then deploy the frontend. Keep the existing every-minute cron job enabled as the retry/fallback path. Do not rerun the cron setup SQL if the job is already active.

## 2. Frontend build
```bash
npm ci
cp .env.example .env.production        # fill in the two browser-safe values
npm run typecheck && npm test && npm run build   # output in dist/
```
Environment variables (browser-safe ONLY): `VITE_SUPABASE_URL`, `VITE_SUPABASE_PUBLISHABLE_KEY` (publishable/anon key), optional `VITE_APP_URL`, and the `VITE_FIREBASE_*` web app values when enabling browser push.
**Never** put the service-role/secret key, database password or SMTP credentials in any `VITE_` variable: everything with that prefix is public in the built JavaScript.

## 3. Hosting
Any static host works (Cloudflare Pages, Netlify, Vercel, S3+CDN). Requirements:
- **SPA fallback**: all unknown paths must serve `index.html` (e.g. Netlify `/*  /index.html  200`, Vercel rewrite to `/index.html`).
- HTTPS only; redirect HTTP to HTTPS.
- PWA and web-push support use `public/firebase-messaging-sw.js` at the site root with scope `/`; the worker caches the app shell and displays data-only FCM messages. `public/sw.js` remains as a compatibility shim for existing installations. HTTPS is required in production (localhost is allowed for development). Test the browser's Install app action, installed launch, and offline app shell after deployment. On iPhone/iPad, use Safari's Share menu > Add to Home Screen before enabling web push.
- Keep `/firebase-messaging-sw.js`, `/sw.js`, `/manifest.webmanifest`, and `index.html` revalidated rather than long-lived immutable; hashed files under `/assets/` can use long-lived immutable caching.
- **whiteshirt.fun pop-up (Profile > Edit):** the app opens `https://www.whiteshirt.fun/?ref=ecomedge` inside a dialog (an iframe) and in its pop-up fallback, so Whiteshirt registrations that follow this link receive the referral parameter. If you add a CSP, include `frame-src https://www.whiteshirt.fun https://whiteshirt.fun`. The pop-up only works if **whiteshirt.fun itself allows being framed**: check with `curl -sI https://www.whiteshirt.fun/ | grep -i -E "x-frame-options|content-security-policy"`. If you see `X-Frame-Options: DENY/SAMEORIGIN` or a CSP `frame-ancestors` that does not list your CampusConnect origin, ask whoever hosts whiteshirt.fun to allow your CampusConnect domain in `frame-ancestors` (and remove X-Frame-Options). Until then the dialog shows a one-click fallback that opens a small separate window. CampusConnect account sign-ups remain separate and do not use Whiteshirt referrals.
- Recommended response headers: `Content-Security-Policy` allowing only your origin, `https://*.supabase.co` (API/Realtime wss), and images from `https://*.supabase.co`; `X-Content-Type-Options: nosniff`; `Referrer-Policy: strict-origin-when-cross-origin`; `X-Frame-Options: DENY`. Test the CSP in staging; Realtime needs `wss://*.supabase.co`.
- Cache `dist/assets/*` for a long time (hashed filenames); do not cache `index.html`.

## 4. First owner
See README "Become the owner". `provision_owner` is callable only from the SQL editor / postgres role and works once.

## 5. Go-live checklist
Run `docs/SECURITY_CHECKLIST.md`, run the SQL test suites (docs/TESTING.md) against the target project, run Supabase security + performance advisors, add real institutions (Admin > Institutions), set the support email (Admin > Settings), have a lawyer review the Privacy/Terms/Guidelines drafts.

## 6. Rollback
Frontend: redeploy the previous build. Database: migrations are forward-only; write a new corrective migration. For data loss, restore from backup into a scratch project first, then copy rows back deliberately.

## 7. Monitoring
Use Supabase Logs (API, Auth, Postgres) and the advisors weekly. Frontend error reporting is not wired yet: add a provider (e.g. Sentry) behind an env var and scrub message bodies from any payload.
